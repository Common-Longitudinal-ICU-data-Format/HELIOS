What we are building

CLIF stores ICU data as columnar parquet, one row per measurement. Agents consume FHIR, because that is what every EHR exposes. HELIOS makes CLIF readable as FHIR, then puts an MCP layer on top so an agent asks for data as tool calls instead of HTTP.

12CLIF tables in scope
6FHIR resource types
~145Msource rows
54LOINC codes to curate
Two services, one-way dependency. helios-fhir is a read-only FHIR R4 server over CLIF parquet — it runs standalone and knows nothing about agents. helios-mcp exposes tools to agents and speaks only FHIR REST upward. It holds no data and never touches parquet. Delete helios-mcp and the FHIR server still works with curl.

Decisions

#DecisionConsequence
1Read-onlyNo POST/PUT/DELETE. Parquet never mutated, no reset logic, reproducible by construction. Write verbs → 405.
2CLIF Beta tables only, minus code_status12 tables. crrt_therapy and ecmo_mcs excluded although the files exist.
3Hybrid terminologyStandard codes where the data has them; curated LOINC for vitals + labs; CLIF-native local CodeSystems elsewhere.
4Static bearer + real SMART scopesReal discovery doc, real scope enforcement, real 401/403. No JWT ceremony. Localhost only.
5Per-request as-of clockX-As-Of filters every *_dttm to <= T. Blocks look-ahead leakage in evals.
6Native MIMIC datesNo shifting. Stays remain in the 2100s. No offset table, no timestamp transforms.
7Lazy translate-on-readFHIR resources are projections built per request and discarded. Nothing materialised.
8Searches need patient contextKeeps every query prunable. Matches Epic, which mandates patient on nearly every search.

Why lazy, not materialised

 EAGER / MATERIALISED  (what MedAgentBench + HAPI JPA do)
   build step ──► translate every CLIF row ──► store ~145M FHIR resources
                                                      │
   request ─────────────────────────────────────────► └─► read one out
   • fast reads   • mapping change = full rebuild   • parquet & FHIR can drift

 LAZY / TRANSLATE-ON-READ   ◄── chosen
   request ──► query parquet ──► translate the ~40 rows that matched ──► respond
                                                                          │
                                                            discarded ◄───┘
   • nothing stored  • mapping change = restart  • cannot drift, one copy of the data

FHIR JSON runs 10–50× the size of columnar parquet, so materialising 1.1 GB produces tens of GB plus a multi-hour build, rebuilt on every mapping change. Both hard constraints make it worse rather than better: the as-of clock means the useful unit is "rows before T", which a resource store does not help with, and decision 1 removes the writes materialisation exists to serve. Lazy makes the FHIR layer a function, not a copy.

Storage layout — settled by our own benchmark

The 12 tables get re-sorted by hospitalization_id once, offline. Not a guess — clif_partition_benchmark/results/report.md measured it. Bytes a reader must touch, labs, cohort size 100:

sorted by hospitalization_id
14.3 MB
hive by 10k-hosp bucket
17.7 MB
single, unsorted
61.5 MB
single, sorted by year
61.9 MB
hive by year
62.5 MB

The mechanism is row-group min/max statistics. Sorting by hospitalization_id makes them tight and non-overlapping, so the reader skips row groups without decompressing them. Partitioning by year cannot help — an ID predicate carries no year information to prune on. A FHIR server's characteristic query is a single hospitalization: the regime where sorting wins ~4× and partitioning wins nothing.

Alongside it, an encounter index: 546,028 rows of (hospitalization_id, patient_id, admission_dttm, discharge_dttm), ~15 MB, held in memory. It answers identity resolution and stay bounds without touching a fact table.

Resource identity

Patient.id = patient_id; Encounter.id = hospitalization_id, both straight from CLIF. Fact rows have no natural key, so resource ids are content-addressed rather than surrogate:

{table}-{hospitalization_id}-{epoch_seconds}-{category}-{sha1(full_row)[:8]}

The trailing hash is not optional. Measured on this export, the key without it is not unique:

vitals — colliding keys
710,555
labs — colliding keys
36,992

Without the hash, GET /fhir/Observation/{id} would be ambiguous for roughly 750,000 resources. The hash is safe because full rows are unique — vitals has 55,525,580 rows and 55,525,580 distinct full rows, zero exact duplicates. Read-by-id stays a lazy lookup with no id-to-row index, and ids stay stable across restarts because they are derived from data rather than assigned.

Three tables need dedup for the hash to hold

Full-row uniqueness was checked across all 12 in-scope tables. Nine are clean. Three are not:

TableRowsExact duplicates
patient_procedures1,045,7299,310  (0.89%)
hospital_diagnosis6,364,488199  (0.003%)
position3,157,9962
the other nine tables0

These rows are byte-identical, so no hash can separate them. prepare_data.py applies SELECT DISTINCT to these three during the Phase 0 rewrite.

Dedup, not an ordinal. A duplicate hospital_diagnosis row is the same ICD code recorded twice; a duplicate patient_procedures row is the same CPT billed twice. Billing artifacts, not two real events. Two identical Condition resources under different ids would show an agent the same diagnosis twice — preserving a distinction that does not exist. Contrast vitals, where colliding rows differ in value and must be kept separate. prepare_data.py asserts full-row uniqueness after the rewrite and fails the build otherwise.

Why the keys collide — and what it costs

The collisions are not noise. They are two devices measuring the same thing at the same minute:

20000147  2121-08-31 23:00  map  75.0  Arterial Blood Pressure mean
20000147  2121-08-31 23:00  map  79.0  Non Invasive Blood Pressure mean

CLIF's vital_category collapses arterial-line and non-invasive cuff into a single map. The distinguishing information survives only in vital_name.

A-line and cuff pressures are not interchangeable for vasopressor titration. An agent handed 75 and 79 for the same instant, with no way to tell them apart, has a contradiction it cannot resolve. Every mapper MUST preserve the CLIF *_name column — *_category is the primary code.coding, *_name goes to Observation.method.text. 1,416,321 vitals rows are affected.

Request flow

GET /fhir/Observation?patient=P123&code=creatinine with X-As-Of: 2110-03-15T08:00:00Z

 1  auth.py     bearer -> scopes; require system/Observation.rs
 2  search.py   reject if no patient/encounter context (400 + OperationOutcome)
 3  store.py    encounter index point-lookup -> hospitalization_id, stay bounds
 4  store.py    one DuckDB query against the sorted parquet:
                  WHERE hospitalization_id = 'H456'
                    AND lab_category      = 'creatinine'
                    AND lab_result_dttm  <= '2110-03-15 08:00:00'
 5  DuckDB      column pruning     -> 5 of 14 columns
                row-group pruning  -> min/max on hospitalization_id
                -> ~40 rows out of 44,880,526
 6  mappers/observation.py   rows -> FHIR Observation dicts
 7  app.py      wrap in searchset Bundle, serialise, respond
 8  ─────────── resources garbage collected, nothing persisted ───────────

The clock

clock.py has one job: parse X-As-Of and return a SQL predicate. No timestamp transformation exists anywhere in the server. When X-As-Of is absent the default is the encounter's discharge_dttm — the whole stay.

Because dates are native MIMIC, anything supplying "now" must speak MIMIC time. A prompt saying "it is 2023-11-13" against a patient admitted 2110-03-14 returns empty bundles, correctly. Harnesses pin the clock relative to admission_dttm.

Each table declares its own clock column:

TableClock column
vitals, patient_assessments, position, respiratory_supportrecorded_dttm
labslab_result_dttm
medication_admin_continuous / _intermittentadmin_dttm
adtin_dttm
patient_proceduresprocedure_billed_dttm
hospitalizationadmission_dttm
hospital_diagnosisnone — no timestamp exists
Known hole. hospital_diagnosis carries no timestamp, so Condition cannot be as-of filtered. Discharge diagnoses are knowable only at discharge, so exposing them to an agent reasoning at hour 24 leaks the future. Documented rather than hidden; mitigation is a scope decision for the harness, not a server fix.

Auth

/.well-known/smart-configuration advertises the token endpoint, supported scopes and client_credentials. Tokens come from a tokens.yaml:

tokens:
  agent-readonly:   [ "system/Patient.rs", "system/Observation.rs", "system/Encounter.rs" ]
  agent-labs-only:  [ "system/Patient.rs", "system/Observation.rs" ]

Enforcement is real — unknown token → 401 + WWW-Authenticate; valid token lacking the scope → 403 + OperationOutcome. In real SMART the only output of the whole JWT/JWKS dance is a bearer token with a scope list, so the JWT flow can replace token lookup later without touching enforcement.

Every error body is a real OperationOutcome. An agent parsing a plain-text 500 learns nothing; an OperationOutcome tells it whether to retry, narrow, or give up.

Dependencies deliberately few: fastapi, uvicorn, duckdb, fhir.resources, pyyaml. clifpy is not a dependency — it loads whole tables into pandas with filters, the wrong shape for per-request serving. CLIF schemas remain the contract; they are just not read through clifpy.

Testing

fhir.resources gives pydantic schema validation free, so tests target semantics:

  1. Mapper unit tests — CLIF row dict in, valid FHIR resource out, asserting system + code.
  2. Look-ahead tests (highest value) — with X-As-Of mid-stay, assert no returned row has a clock column after T. Per table, since each has its own clock column. This protects the benchmark's validity and is most likely to regress silently.
  3. Scope enforcement — 401 with no token, 403 with the wrong scope, 200 with the right one.
  4. Contract tests — search without patient context is 400; microbiology is 200 + empty; every write verb is 405.
  5. Golden file — one real hospitalization rendered to FHIR, checked in and diffed.
  6. Resource-id uniqueness — every generated id distinct, and GET /fhir/{Type}/{id} round-trips to the row it came from. The test that would have caught the 750,000 ambiguous ids.

Phases 1–4 leave helios-fhir independently runnable and testable. Phase 5 starts only after the FHIR server is complete — that is what keeps the dependency one-way.

Known limitations

  1. Condition cannot be as-of filtered — hospital_diagnosis has no timestamp. A real look-ahead hole.
  2. LOINC coverage is 54 curated rows. Medications and assessments are CLIF-native only; an agent expecting RxNorm will not find it.
  3. Searches without patient context are refused rather than served. Deliberate, matches Epic, but a genuine deviation from unrestricted FHIR search.
  4. Microbiology endpoints exist but this export has no data behind them.
  5. Dates are in the 2100s. Anything supplying "now" must speak MIMIC time.
  6. patient_procedures, hospital_diagnosis and position are deduplicated at prepare time (9,310 / 199 / 2 rows dropped). Served row counts will not match the raw parquet.
  7. vital_category is lossy: arterial and non-invasive blood pressure share the sbp/dbp/map categories. Preserving vital_name in Observation.method recovers the distinction, but an agent filtering on category alone will still mix measurement methods. 1,416,321 rows affected.
